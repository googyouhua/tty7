topic: Docker 容器作为 tty7 主机
updated: 2026-11-01T02:44

- (requirement) R1 (prd FR-1,FR-2,FR-4): 本机运行中的容器出现在连接器里，可与 SSH/WSL 并列搜索；手动按名字或 ID 也可接入；连接标识 docker:<name> 不与同名 WSL 发行版冲突
- (requirement) R2 (prd FR-3): 接入容器得到完整 workspace，文件树/git/diff/搜索作用在容器内文件系统，tab 与布局按既有规则持久化
- (requirement) R3 (prd FR-5): 首次向某容器写入服务端程序前必须确认；确认过一次后同一容器（含重建后）不再询问
- (requirement) R4 (prd FR-6): 装机使用容器架构对应的静态 musl 资产，宿主与容器架构不同也能成功；无法识别架构时中止并说明哪一侧不支持
- (requirement) R5 (prd FR-7): HOME/rootfs 不可写或挂载 noexec 时按优先级回退安装位置，全部不可写时列出尝试过的路径
- (requirement) R6 (prd FR-8,FR-12): 典型镜像首次装机从确认到可进入 ≤15s；已装好时接入无额外等待；交互开销不随 pane 数线性增长
- (requirement) R7 (prd FR-9): 容器身份是容器名；compose down/up 后连接器仍只一行，tab 与布局保留，pane 明示容器已重建且已停止
- (requirement) R8 (prd FR-10): 容器停止或 docker 未运行时条目保留并标不可用，恢复后自动可用且无需重新确认装机；容器被彻底删除时条目保留并标找不到
- (requirement) R9 (prd FR-11): 关闭 workspace/tty7 或断开后容器内不残留该次连接启动的进程；客户端被强杀后残留进程在有限时间内自行退出
- (requirement) R10 (prd FR-13): 七类失败各自给出可读原因与可执行下一步，且都不表现为无限等待
- (requirement) R11 (prd FR-14): DOCKER_HOST/docker context 指向远端守护进程时明确拒绝；该配置下本机容器仍可用
- (constraint) C1 (prd §5): 容器内不得安装 sshd，也不得要求容器具备出网能力
- (constraint) C2 (prd §5): 只支持有 POSIX shell 的容器；distroless/scratch 不支持，给可读错误而非降级
- (constraint) C3 (prd §5,§6.2): 容器内执行沿用 docker exec 默认用户（镜像 USER），v1 不做降权或用户选择
- (constraint) C4 (addendum §1): 复用既有本地 exec 通道与远端装机抽象，不新增线上协议；容器是这条通道的第三个实例
- (constraint) C5 (prd §5): tty7 不起停容器、不构建镜像、不解析 compose 项目
- (constraint) C6 (prd §5): SSH 与 WSL 主机类型的既有行为不变
- (assumption) A1: 同名不同镜像的容器不额外提示，按同一主机处理（prd §9），待可用性验证
- (assumption) A2: pane 默认工作目录是容器内该用户的 HOME，不可用时回退 /（prd §9）
- (assumption) A3: 容器被彻底删除后条目保留，由用户决定清理，v1 不提供删除入口（prd §9）
- (assumption) A4: 现有 musl 双架构资产已覆盖容器场景，不为容器新增构建矩阵（addendum §3.2）
- (question) Q1: Windows 上同名 WSL 发行版 docker-desktop 与同名容器并存时的区分是否足够（prd §8.1）
- (question) Q2: 安装目录回退优先级具体顺序，需在 root/非 root/只读 rootfs/noexec 一组镜像上实测（prd §8.2）
- (question) Q3: 客户端被强杀后容器内进程自行退出的时间上界，决定 R9 的可测阈值（prd §8.3）
- (question) Q4: 同名不同镜像是否真的无需提示，需可用性验证（prd §8.4）
- (question) Q5: 是否需要删除容器主机记录的显式入口（prd §8.5）
- (question) Q6: Windows 上 docker CLI 的发现方式（PATH/Docker Desktop/WSL 内 docker），影响 R1 在 Windows 的首行代码（prd §8.6）
- (constraint) C7 (prd §7 SM-C3): 容器列表刷新不得变成常驻高频 docker ps 轮询
- (event) SPEC self-validate Pass 1 (coherence): 通过——C7 与 Podman 边界为回填项，已补
- (event) SPEC self-validate Pass 2 (preservation): 通过——PRD FR-1..FR-14 全部落到 R1..R11；§5 与 §6.2 落到 C1-C7 与 Boundaries
- (decision) 切片：只一条 epic (epic-docker-hosts, covers R1-R11)。理由：同一批文件、无部署边界、分开交付会让首版缺 R7/R8 正是 PRD 要消除的体验
- (decision) 不设独立平台基线 epic：基线(docker CLI 发现、容器枚举)由这条 epic 的头两条 story 承担
- (decision) tracer: 发现容器 → 首次确认装机 → 进入 workspace → 断开回收
- (event) Tree/Dependencies 校验：pass-with-fixes；补 RouteTarget::origin_key touch point 与平台基线 Decision 后通过
- (decision) 批准单 epic 交付 R1-R11；R11 不后置；切 story 前先用 spike 钉死 Q2(安装目录回退)与 Q3(强杀退出上界)
- (decision) v1 只做 macOS/Linux；Q1(同名 docker-desktop)与 Q6(Windows CLI 发现)后置 v2，不再是 R1 的 v1 阻塞项
- (requirement) R9 改写(阈值来自 spike 1.2)：桥在 1s 内退出（实测 ≤56ms）；允许且只允许一个常驻 daemon 被复用，不随连接累积
- (decision) Q3 关闭：正常关闭/SIGTERM/SIGKILL 三情形实测 52-56ms，阈值取 1s（一个数量级余量）
- (requirement) R5 改写(阈值来自 spike 1.3)：顺序 HOME/.local/share/tty7/bin → /tmp/tty7-<uid>/bin → /run/user/<uid>/tty7；/dev/shm 退出候选(Docker 默认 noexec)
- (decision) 只读 rootfs 且无 exec tmpfs = 无可用安装位置，报错而非降级；该场景归入 R10 的『无可写安装目录』
