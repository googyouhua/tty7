# PRD: Docker 容器作为 tty7 主机

*工作标题，待确认。*

## 0. Document Purpose

这份 PRD 面向实现它的开发者、做架构决策的 Winston、以及把能力拆成 epic 的 Sofia。术语以 §3 词汇表为准，功能成组、FR 全局编号，推断项用 `[ASSUMPTION]` 就地标注并在 §9 汇总。技术机制、备选方案与被否决的路线放在同目录的 `addendum.md`，正文不承载"怎么做"。上层容器是 `_bmad-output/initiative-docker-hosts/initiative-docker-hosts.md`，它只留 Outcome 与边界，需求以本文为准。

## 1. Vision

tty7 今天能接两种主机：SSH 远端，和本机的 WSL 发行版。两者之间空着一块——**容器**。它比 SSH 更近（就在本机），比 WSL 更常见（每个项目的依赖隔离都靠它），却是三种里最难接的一种：里面一般没有 sshd，也不该为了让人连进去而装一个；容器常常没有出网，装不了任何东西。

结果是，用容器开发的人被迫退回到"手敲 `docker exec -it`"的原始形态：没有文件树、没有 git 面板、没有持久 tab，关掉窗口就什么都没了。而容器恰恰是最需要这些的场景——它的文件系统和宿主是隔离的，你没法用宿主的编辑器去改它里面的东西。

这件事做成之后，容器在 tty7 里和一台机器没有区别：在连接器里选中它，得到完整的 workspace，tab 布局和 pane 跟着它走，容器重建了还能回来。用户不需要知道容器里有几层、有没有 sshd、二进制是怎么进去的——**"能不能连"不应该取决于镜像作者有没有预留一个后门**。

## 2. Target User

### 2.1 Jobs To Be Done

- **功能**：在一个隔离的、可重建的环境里跑构建、测试和长任务，同时保留我在 tty7 里已有的工作方式（多 tab、命令块、git 面板）。
- **功能**：把"这个项目的环境"和"我这台机器"解耦，换机器或换同事时环境一致。
- **情绪**：不想因为"容器里没有 sshd"就被迫换工具，或者被迫往镜像里塞一个 SSH 服务。
- **情绪**：容器重建是常态，不该每次重建都像重新入职。
- **情境**：一天里会在宿主和容器之间来回切几十次，切过去必须是零成本。

### 2.2 Non-Users (v1)

- 只想在容器里跑一条命令、不要 workspace 的人：`docker exec` 已经够用，本 PRD 不服务这个场景。
- 把容器当生产运行时、要通过 tty7 运维线上容器的人：v1 的信任模型是"这是开发者自己的机器"。
- 使用 `distroless` / `scratch` 之类没有 POSIX shell 镜像的人：见 §5。
- 通过 `DOCKER_HOST` 或 docker context 连远端 docker 守护进程的人：见 §5。

### 2.3 Key User Journeys

> **UJ-1. 林舟的早上：容器已经在跑，点进去就能干活。**
> 林舟负责一个 Rust 服务，用 `docker compose` 起开发环境。早上开机，`docker compose up -d` 之后打开 tty7，连接器里已经有 `api-dev` 这一行——昨天留下的，不是今天新建的。点进去，昨天的三个 tab 还在原处，`cargo test` 的 pane 停在上次的输出上。她按 ↑ 回车，继续跑。**全程没有出现"正在安装"、"正在连接"以外的任何提示。**

> **UJ-2. 新同事第一次接：确认一次，十五秒后进入。**
> 程一的机器上第一次出现这个容器。他在连接器里选中 `api-dev`，tty7 说需要往容器里放一个 12MB 的服务端程序，问是否允许。他点允许，进度条走完，进入 workspace。之后这台机器上他再也没见过这个弹窗——包括他把容器删了重建之后。

> **UJ-3. 容器重建：布局回来，内容不假装还在。**
> 林舟改了 `docker-compose.yml` 里的镜像版本，`docker compose down && docker compose up -d`。容器 ID 变了、名字没变。回到 tty7 点 `api-dev`，没有出现重复的第二行，没有重新问安装，直接进入。tab 和分组还在，pane 明确告诉她"容器已重建，这些 pane 已停止"，而不是给一片空白让她以为程序挂了。

> **UJ-4. 连不上：说清是哪一种连不上。**
> 程一把镜像换成了 `alpine` 之后删了 shell，或者拉了一个 amd64 镜像跑在 arm64 的 Mac 上。他点进去，看到的是一句人话——"这个容器里没有可用的 `/bin/sh`，tty7 的 pane 需要它"或者"容器是 linux/amd64，而本机可用的服务端程序是 linux/arm64"——外加他能做的下一步，而不是一个转圈然后超时。

## 3. Glossary

- **容器主机** — 一个正在运行的 Docker 容器，被 tty7 当作一台独立的主机接入。v1 一个容器主机对应恰好一个容器；不聚合 compose 项目。
- **连接器** — tty7 里列可选主机的界面，SSH profile、直连、WSL 发行版、容器主机都出现在这里。
- **tty7-server** — 跑在主机一侧的无特权服务端程序，承载文件、git、pane 与会话状态。在容器主机里，它就是被装进容器的那个可执行文件。
- **装机** — 把 `tty7-server` 放进容器并置为可执行的过程。
- **长驻通道** — 一条承载控制连接与全部 pane 流量的持续存在的 `docker exec` 会话。一个容器主机在一条连接里只有一条长驻通道。
- **容器身份** — 判定"两次连接是不是同一个容器主机"的依据。v1 用容器**名字**，不用容器 ID。
- **复用** — 容器重建后，按容器身份重新接管已有的 workspace 记录，而不是新建一条。
- **孤儿** — 客户端已经断开、却仍在容器内运行的 `tty7-server` 进程。

## 4. Features

### 4.1 发现与进入

**Description:** 容器主机出现在连接器里，和 SSH 主机、WSL 发行版并列，用同一套搜索和键盘操作。列表来自本机 docker 守护进程，实时反映运行状态。用户不需要先"注册"一个容器——容器在跑，它就在列表里。实现了 UJ-1、UJ-2。

**Functional Requirements:**

#### FR-1: 列出本机运行中的容器

用户可以在连接器里看到本机所有**运行中**的容器，每行显示容器名与镜像名。实现 UJ-1。

**Consequences (testable):**
- docker 守护进程可用时，正在运行的容器在连接器打开后 2 秒内出现；新起的容器在下一次打开连接器时出现，无需重启 tty7。
- 已停止的容器不出现在默认列表里。
- 列表项可以像 SSH 主机一样被搜索命中（按容器名或镜像名）。
- docker 守护进程不可用或未安装时，列表为空且不报错；容器主机这一组不出现，其余主机类型不受影响。

#### FR-2: 手动指定一个容器

用户可以按容器名或容器 ID 手动输入，接入不在列表里的容器（例如刚启动、列表尚未刷新）。实现 UJ-3 的兜底路径。

**Consequences (testable):**
- 输入不存在的容器名时，给出"找不到这个容器"的明确错误，而不是挂起等待。
- 手动接入与列表接入产生同一个容器主机与同一个 workspace 记录，不因入口不同而重复。

#### FR-3: 一个容器主机就是一个 workspace

用户接入容器主机后得到与 SSH 远端、WSL 相同的完整能力：文件树、git 状态、diff、多 tab、分组、持久 pane。实现 UJ-1。

**Consequences (testable):**
- 文件树、git 面板、diff、搜索都在容器内的文件系统上生效，不读宿主路径。
- pane 的 shell 工作目录默认落在该用户在容器内的 `HOME`；`HOME` 不可用时回退到 `/`，并在 pane 启动时给出说明。
- 关闭 tty7 后重新打开，workspace 的 tab、分组、pane 布局按既有持久化规则恢复。

#### FR-4: 与其它主机类型的区分

容器主机在连接器里有稳定的类型标识，不与同名 WSL 发行版或 SSH 主机混淆。

**Consequences (testable):**
- 在 Windows 上同时存在名为 `docker-desktop` 的 WSL 发行版与容器时，两者出现在不同的分组里，标签不冲突。
- 容器主机的连接标识形如 `docker:<容器名>`，WSL 的是 `wsl:<发行版名>`，两者不会互相命中。

### 4.2 装机

**Description:** 容器里不会有 `tty7-server`，tty7 把它送进去。用户只在第一次看到确认，之后（包括容器重建后）静默完成。实现了 UJ-2、UJ-3。

**Functional Requirements:**

#### FR-5: 首次装机需要用户确认

用户第一次把某个容器主机接入时，tty7 说明将要在容器内写入的文件、来源与大小，并获得确认。实现 UJ-2。

**Consequences (testable):**
- 未经确认不向容器写入任何文件。
- 用户拒绝时连接中止，不留下部分写入的文件，且下次接入仍会询问。
- 确认过一次之后，同一容器身份的后续接入不再询问，包括容器重建之后。

#### FR-6: 按容器架构与 libc 选择资产

装机使用与容器匹配的服务端程序，而不是与宿主匹配的那一个。

**Consequences (testable):**
- 容器为 `linux/amd64` 时装 `x86_64-musl` 资产，`linux/arm64` 时装 `aarch64-musl` 资产，即使宿主架构不同。
- 架构无法识别或没有对应资产时，连接中止并说明是哪一侧不受支持，不尝试用错架构的二进制。
- 静态 musl 二进制在 Alpine 与常见 glibc 发行版上都能运行。

#### FR-7: 安装位置在没有写权限时回退

装机不假设容器内的 `HOME` 可写，也不假设 rootfs 可写。

**Consequences (testable):**
- 按固定优先级尝试安装目录，第一个可写的位置胜出；全部不可写时，给出列出尝试过哪些路径的错误。
- 安装目录与 `tty7-server` 已在的旧版本一致时不重复写入；版本或方言不匹配时按既有规则替换。
- 只读 rootfs、`noexec` 挂载、非 root 用户三种情况下，各自给出可读原因。

**Notes:** 优先级的具体顺序留待架构确定，PRD 只约束"必须回退"与"必须可解释"。

#### FR-8: 装机成本可接受

装机不应让用户等到怀疑卡死。实现 UJ-2。

**Consequences (testable):**
- 典型镜像上首次装机从确认到可进入不超过 15 秒（局域网、12MB 量级二进制）。
- 已装好且版本匹配时，接入不产生额外的装机等待。
- 每次接入用于探测容器状态的外部进程调用次数是有界的、少量的，不随 workspace 数量线性增长。

### 4.3 生命周期与身份

**Description:** 容器是反复重建的东西。身份、状态与资源回收必须围绕这一点设计，而不是围绕"一次连接"。实现了 UJ-1、UJ-3。

**Functional Requirements:**

#### FR-9: 容器身份是名字，不是 ID

同一个名字的容器，即使 ID 变了，也视为同一个容器主机。

**Consequences (testable):**
- `docker compose down && up` 之后再次接入，连接器里仍只有一行，不产生第二条记录。
- 复用的 workspace 保留其 tab、分组与布局；pane 因为原容器已不存在而处于停止状态，并显示"容器已重建，pane 已停止"，不显示为空白或成功。
- 名字相同但镜像不同的容器，按同一容器主机处理。

**Notes:** `[ASSUMPTION: 名字相同、镜像不同时不额外提示，因为 compose 换镜像版本是日常操作，提示会成为噪音。若用户需要区分，v2 再加。]`

#### FR-10: 容器停止时记录保留

容器停止或 docker 未运行时，容器主机条目继续存在，但明确显示为不可用。实现 UJ-3。

**Consequences (testable):**
- 容器停止后，条目仍然出现在连接器里并标记为未运行；点击时给出"容器未运行"的说明，并附上容器的当前状态。
- 容器重新运行后，该条目自动恢复为可用，无需重建条目或重新确认装机。
- 容器已彻底删除（名字也不存在了）时，条目保留并标记为找不到，由用户决定删除。

#### FR-11: 断开必须回收容器内进程

客户端断开后，容器内不得留下孤儿 `tty7-server`。

**Consequences (testable):**
- 关闭 workspace、关闭 tty7、或从连接器断开后，容器内不残留由该次连接启动的 `tty7-server` 进程。
- 由于 `docker exec` 不提供信号代理，回收依赖通道自身的 EOF 语义；该机制必须有自动化验证，不能只靠人工观察。
- 进程被强杀（kill -9 客户端）后，容器内的进程在有限时间内自行退出；超过该时间仍存活的残留，下一次接入时能被识别并清理，或至少被报告。

**Notes:** 这是本 PRD 里风险最高的一条，理由是 Docker 在协议层无法杀掉 exec 进程（见 addendum 的证据）。验证方式在架构阶段确定。

#### FR-12: 一条连接只用一条长驻通道

一个容器主机的控制连接与全部 pane 共用一条长驻 `docker exec` 会话。

**Consequences (testable):**
- 打开 5 个 pane 不产生 5 条独立的 `docker exec` 会话。
- 单次交互的额外开销不随 pane 数量增长；高频小命令（如文件树展开）不逐个触发新的进程调用。

**Notes:** 单次 `docker exec` 的成本约 0.4 秒（见 addendum），这是硬约束，不是优化项。

### 4.4 失败与诊断

**Description:** 容器环境的不确定性远高于 SSH 主机。每一种可预期的失败都要有自己的话，而不是统一变成超时。实现 UJ-4。

**Functional Requirements:**

#### FR-13: 失败原因分类且可操作

连接失败时，用户能看到属于哪一类问题，以及下一步该做什么。

**Consequences (testable):**
- 以下情形各自有不同的、面向用户的说明：容器未运行；docker 守护进程未运行；容器内没有可用的 `/bin/sh`；容器架构没有对应资产；容器内无任何可写安装目录；装机被用户拒绝；装机完成但服务端无法启动。
- 每类说明都包含用户可执行的下一步（例如"在容器内安装 sh 或换一个镜像"），而不是只给错误码。
- 任何一类失败都不表现为无限等待：连接在有限时间内失败或有明确进度。

#### FR-14: 拒绝远程 docker 守护进程

通过 `DOCKER_HOST` / docker context 指向远端守护进程时，v1 明确不支持。

**Consequences (testable):**
- 检测到远端 docker 守护进程时，给出"v1 只支持本机容器"的说明，而不是尝试连接并失败于某个更底层的原因。
- 本机与远端混合的配置下，本机容器仍然可用。

## 5. Non-Goals (Explicit)

- **不往容器里装 sshd，也不要求镜像提供 SSH。** 这是本功能存在的理由。
- **不要求容器有出网能力。** 二进制从宿主送进去；任何"连不上外网就装不了"的路径都是缺陷。
- **不做没有 POSIX shell 的容器（distroless / scratch）。** tty7 的 pane 本身需要 shell，没有 shell 的容器当终端主机没有意义。v1 给出可读错误，不静默降级。
- **不通过 `DOCKER_HOST` / docker context 支持远端 docker 守护进程。** 那是"连另一台机器"，与"连本机容器"是两个问题。
- **不起停容器、不构建镜像、不解析 compose 项目。** 容器由用户自己的编排工具管理。
- **不做容器之间的分组与聚合。** 一个容器就是一台主机，平铺。
- **不改变 SSH 与 WSL 主机类型的行为。** 本功能复用它们的通道，但它们的语义不变。
- **不做"容器里以 root 运行"的安全加固。** v1 沿用 `docker exec` 的默认用户；降权与用户选择属于后续。

## 6. MVP Scope

### 6.1 In Scope

- 运行中容器的发现、搜索、手动接入。
- 容器主机作为完整 workspace：文件、git、diff、多 tab、持久化。
- 首次确认后静默装机，按容器架构选资产，安装目录回退。
- 按名字复用容器身份，容器重建后布局保留、pane 明示已停止。
- 容器停止/删除后的条目状态与恢复。
- 断开回收、无孤儿。
- 失败分类与可操作提示，远端 docker 的明确拒绝。

### 6.2 Out of Scope for MVP

- 无 shell 镜像（distroless）支持 —— 需要一套不经 shell 的远端操作协议，与 v1 的复用策略冲突。
- `DOCKER_HOST` / 远端 docker context —— 网络形态完全不同，见 §5。
- 手动指定容器内执行用户（`docker exec -u`）—— 默认用户已覆盖绝大多数开发镜像；需要时再加。
- 容器起停入口（在连接器里"启动这个容器"）—— v1 只读状态，不改状态。
- compose 项目分组 —— 平铺足够，分组需要定义"项目"的边界。
- Podman / nerdctl 等其它容器运行时 —— 通道形状相同，但资产与命令差异需要单独验证，`[NOTE FOR PM]`：如果实现层抽象干净，这一项可能便宜到可以直接并入 v1。

## 7. Success Metrics

**Primary**

- **SM-1**: 从"在连接器里选中一个已运行过的容器"到"能在 pane 里敲下第一条命令"，交互次数 ≤ 2（选中 + 首次确认），旧容器 ≤ 1。验证 FR-1、FR-3、FR-5、FR-8。
- **SM-2**: 容器重建后重新接入，零额外提问、零重复条目。连续 10 次 `down/up` 循环后，连接器条目数恒为 1。验证 FR-9、FR-10。
- **SM-3**: 孤儿率为 0。100 次"接入 → 关闭"循环后，容器内 `tty7-server` 进程数为 0。验证 FR-11。

**Secondary**

- **SM-4**: 首次装机在测试矩阵的典型镜像上 ≤ 15 秒（p90）。验证 FR-8。
- **SM-5**: 失败场景中，用户能从提示文字直接判断下一步的比例 ≥ 90%（对 §4.4 列出的 7 类失败逐条人工核验）。验证 FR-13。

**Counter-metrics (do not optimize)**

- **SM-C1**: 不以"少一次确认"换装机确认弹窗的取消。首次确认是安全边界，为了 SM-1 把它砍掉是反向优化。
- **SM-C2**: 不以"支持更多镜像"换掉"失败要说清楚"。把无 shell、错架构的容器硬塞进正常路径，会让 SM-5 崩掉，而 SM-1 看不出差别。
- **SM-C3**: 不以提高轮询频率换 SM-2 的即时性。容器列表的刷新不能变成常驻高频 `docker ps`。

## 8. Open Questions

1. 同名容器的**并发**情况（同一名字在不同 docker context 下）在 v1 不出现，但 Windows 上 WSL 发行版 `docker-desktop` 与同名容器并存需要实测，确认 FR-4 的区分足够。
2. 安装目录的回退优先级具体是什么？`$HOME` → 某个 `/tmp` 系路径 → 其它？需要在一组真实镜像上实测后确定（影响 FR-7 的验收）。
3. 强杀客户端后容器内进程的自行退出时间上界是多少？这决定 FR-11 第三项的可测阈值。
4. 容器名相同、镜像不同时是否真的不需要提示？目前按不需要处理（FR-9 的假设），但"我换了个镜像，怎么还是旧的布局"可能会成为一个真实的困惑。需要在可用性测试中确认。
5. 连接器里是否需要一个"删除这个容器主机记录"的显式入口？容器被彻底删除后条目会一直留着（FR-10）。
6. Windows 上 `docker` CLI 的发现方式（PATH、Docker Desktop 自带路径、WSL 内 docker）尚未确认，影响 FR-1 在 Windows 上的首行代码。

## 9. Assumptions Index

- §4.3 FR-9 —— 同名不同镜像的容器按同一主机处理，不额外提示。
- §4.1 FR-3 —— pane 的默认工作目录是该用户在容器内的 `HOME`，不可用时回退 `/`。
- §4.1 FR-1 —— 默认只列运行中的容器；已停止的通过记录保留呈现，而不是作为可选主机。
- §4.3 FR-10 —— 容器彻底删除后条目保留，由用户决定清理。
- §4.2 FR-6 —— 现有发布的 musl 资产已覆盖容器场景，不需要为容器新增构建矩阵。
- §2 —— 目标用户是有长期开发容器的开发者，不是一次性调试容器的人。
- §5 —— 无 shell 镜像明确排除，而不是降级支持。
