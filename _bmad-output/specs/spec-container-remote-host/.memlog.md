- (direction) Manage this work through BMad (spec-kernel plus downstream BMad skills), not Comet/OpenSpec (user direction).
- (direction) Prioritize Docker as the container runtime; podman and nerdctl are considered best-effort and not required for v1 (user direction).
- (direction) Target the full devcontainer experience, not just the sidebar icon (user direction); all three mount shapes must work: bind same path, bind different path, and in-container clone.
- (note) Reported symptom: entering a container from a tty7 pane and starting an agent leaves the left sidebar with no agent avatar and no branch.
- (decision) Root cause: tty7 treats a docker-exec pane as the local host. Foreground agent detection reads the host PTY leader argv (/proc/<pid>/cmdline via daemon remote.rs) which is the docker client, and cwd is the shell OSC 7 report or the host foreground process cwd, so neither the in-container agent nor the container repo is ever consulted.
- (decision) Approach is container-as-remote-host: install the static musl tty7-server into the container and speak the daemon protocol over docker exec -i <ctr> <server> --stdio, reusing the remote-workspace plumbing. This covers all three mount shapes because git, agent detection, and cwd all execute inside the container.
- (decision) Reuse existing assets instead of a parallel stack: RemoteTarget variants (LocalStdio/Wsl), RemoteLink::local_stdio, RouteTarget/router, the RemoteOps install pipeline with install/wsl.rs as the non-SSH template, remote-install download and checksum, and the remote Host plus right-panel/file-tree/diff stack.
- (constraint) No pre-install required inside the container image: the server binary is pushed by tty7 (static musl).
- (constraint) The container must be Linux and permit docker exec; the runtime CLI must be reachable and honor DOCKER_HOST/context.
- (constraint) Reuse the remote-workspace plumbing; do not build a parallel host stack.
- (constraint) No privilege escalation beyond the user existing container-runtime access.
- (constraint) Docker is required for v1; podman and nerdctl are best-effort.

- (capability) CAP-2 | intent: on first open tty7 installs and starts its server inside the container so the container becomes a full remote host, without manual steps. | success: a version-matched tty7-server is present and running in the container; reopening the same running container reuses it rather than reinstalling.
- (capability) CAP-3 | intent: the sidebar shows each container pane agent with avatar and status just as for a local pane, independent of the host runtime argv. | success: starting Claude Code or OpenCode inside a container pane shows the brand avatar and the working/waiting/done dot in the sidebar.

- (capability) CAP-5 | intent: shell integration works in the container shell so working directory tracks and new tabs/splits open in place. | success: cd inside the container updates the pane cwd and Info row, and a new split opens in that container directory.

- (assumption) The host build can supply a static musl tty7-server matching the container architecture (x86_64/aarch64), as release assets already do.
- (assumption) The Docker CLI is on the host PATH and the user can list and exec into containers.
- (assumption) A writable and executable location exists inside the container; where only noexec storage is writable, degradation applies.

- (decision) Transport is host IPC, not the container network: the daemon protocol travels over the docker exec stdio channel (docker CLI <-> docker API over the host socket) to the in-container tty7-server --stdio. Container network isolation (bridge, host, none) is irrelevant; no port, IP, or in-container listener is required, and --network none containers work.
- (constraint) Do not depend on the container reaching the GUI over a network; the only network dependency is host-to-docker-daemon (the socket / DOCKER_HOST), which is the user existing docker access. A daemon that is itself remote (DOCKER_HOST over ssh/tcp) is out of scope for v1.

- (decision) Zero container-start changes: tty7 attaches to an already-running container via docker exec, so no change to the container start command (docker run / compose / devcontainer), no image change, and no added flag is required.
- (decision) The host docker socket stays on the host and is never mounted into the container; the host-side docker CLI is its only user. Mounting /var/run/docker.sock into the container is explicitly not part of the design and is a security anti-pattern here.
- (constraint) Must not require mounting the docker socket or adding volumes/flags to the container; the only container-side preconditions are: running Linux container, exec permitted, and a writable-and-executable path.
