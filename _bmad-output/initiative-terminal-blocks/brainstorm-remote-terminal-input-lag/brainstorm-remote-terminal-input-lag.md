# 远程终端经跳板机输入偶发卡顿 — Intent

## 主题 / 目标
远程终端经公网 + 跳板机 SSH，命令执行输出顺畅，但回到输入界面后键入偶发秒级才回显。目标：定位秒级 hold 发生在哪一段，给出可复用验证手段。

## 已确认判据链
1. 执行过程输出顺，只卡输入回显（如 `pwd` 过几秒才显示）。
2. 整包秒级 hold：`pwd` 三字母一起冒出，非逐键 RTT 叠加。
3. idle 后首包卡为主（卡完一次可能就不卡），但连续输入过程中也可能卡。
4. 同机、同样连接方法、基本同一时间段，其他终端不卡。
5. 卡住时只有字不出，UI 其他操作（滚动/切 tab）还活。
6. 本地 WSL 直连不卡；本地和远程 shell 是同一个进程。

## 收敛结论
- 主嫌疑 A：本地 tty7 输入 → 发送 → 等回显 → 渲染链对高 RTT + 跳板敏感。低 RTT（WSL/本地）掩盖问题，高 RTT 放大为秒级。
- B（跳板/传输 idle 冻结与小包策略）/ C（远端 shell/PTY 回显 hold）已半证伪：同机同路同时他端不卡，排除公网/跳板机全局问题；只有字不出排除整窗渲染冻结。但未完全排除，需 parity 对照确认。
- 秒级整包 hold 不像普通 Nagle（~40ms），更像重传超时 / 通道冻结 / 服务端 hold 回显 / 本地 hold 放行（等锁/定时器/上个命令结束标记），需时间戳定位。

## P0 行动（下游直接执行）
1. 四段打时间戳定位秒级 hold：按键采集 → 发包 → 远端 echo 回来 → 渲染。每段记录单调时钟，复现时直接读出卡在哪一段。
2. SSH 参数 parity 核对（tty7 vs 不卡的他端）：ProxyJump / 复用（multiplex）/ 保活（ServerAlive/TCPKeepAlive）/ Nagle（TCP_NODELAY）/ 压缩 / PTY 模式。逐项对齐后复测。
3. 对比抓包 + 路测：同机同时双客户端对照，抓包看输入小包何时发出、何时回 echo；`mtr` + `ssh -vvv` 看首包重传/通道冻结。
4. P1 后续：确认 tty7 是等真回显才画还是有本地预测回显；排查远端 prompt 阻塞（precmd/git status）。

## 明确非目标
- 不先动公网 / 跳板机全局优化（已由同路对照排除为全局问题）。
- 不先改渲染主线程 / 整窗架构（UI 活已排除整窗冻结）。
- 不做输出流优化（输出顺，非问题面）。

## 下游输入
- systematic-debugging / diagnosing-bugs：以四段时间戳 + parity 对照表为首份证据。
- bmad-spec：修法以前必须先有时间戳定位结论，不凭猜测动发送/回显策略。
